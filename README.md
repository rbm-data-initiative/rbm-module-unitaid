# RBM Dashboard Sandbox

Minimal Next.js project that reproduces the setup of the Global Malaria Dashboard (RBM Partnership to End Malaria / UNOPS) so that an external team can develop **one module** that will later be copied into the main project.

This repository is a **GitHub template**. Each external team gets its own repository created from it (`rbm-module-<slug>`), configured by the internal team as described in [docs/github/](docs/github/README.md). The module identity (slug, i18n namespace, env prefix, owners) lives in [`module.config.json`](module.config.json). In the template the module is the placeholder `unitaid`, owned by the internal team on both sides of `CODEOWNERS`; `module:init` replaces it with the team's slug and owners.

Full guide of rules and structure: [Integration guidelines — External dashboard](LINK_TO_DOC).

## Requirements

- Node.js 20 (`nvm use` reads the `.nvmrc`)
- npm (the `package-lock.json` is committed; CI uses `npm ci`)

## Running

```bash
npm ci
cp "src/app/[locale]/unitaid/.env.example" .env.local
npm run dev
# http://localhost:3000/en/unitaid  (also /fr/unitaid and /pt/unitaid)
```

## Where to code

Only these three folders belong to the external team; everything else is the "host" and is protected:

```
src/app/[locale]/unitaid/   # page, components, hooks, services, lib (server-only), types, i18n, docs
src/app/api/unitaid/        # API routes: data (GET proxy) and notifications (POST)
public/unitaid/             # static assets of the module
```

Read `src/app/[locale]/unitaid/README.md` for the responsibility of each subfolder. Tests (`*.test.ts`) live next to the code they cover, inside the first two folders; see [Tests](#tests).

## What not to touch

Any file outside the three folders above (configuration files, `module.config.json`, `src/config.ts`, `src/i18n.ts`, the shell in `src/ui/shell`, `messages/*.json`, `package.json`, `package-lock.json`, `scripts/`, `.github/`). The contract script stores the hash of each of these files in `scripts/protected-files.json` and fails if any of them changes.

Pull requests that touch protected files require approval from the internal team (`.github/CODEOWNERS`), and CI verifies that the manifest itself was generated by the internal team (`PROTECTED_MANIFEST_SHA256` repository variable). Regenerating the manifest yourself does not make a change acceptable.

### New dependencies

The external team cannot add, remove or change the version of any package by itself. `package.json` is protected and `scripts/approved-dependencies.json` is the allow list. Need a library (UI kit, parser, chart type)? Record name, version and justification in section 4 of `src/app/[locale]/unitaid/INTEGRATION.md` and agree with the internal team, who adds it, re-snapshots and opens the pull request. The same package also has to enter the main project, which is why approval happens first.

### Fonts

The host ships Roboto, Inter and Poppins; import them with `import { roboto, inter, poppins } from "@/fonts"`. These files are protected and cannot be changed or removed.

The module **can add its own typefaces**, self-hosted inside the module folder:

```
src/app/[locale]/unitaid/fonts/
├── files/            # one .woff2 per weight/style, max 1 MB each
│   ├── brand-400.woff2
│   └── brand-700.woff2
└── index.ts          # the only file that calls next/font/local
```

```ts
// src/app/[locale]/unitaid/fonts/index.ts
import localFont from "next/font/local";

export const brand = localFont({
	src: [
		{ path: "./files/brand-400.woff2", weight: "400", style: "normal" },
		{ path: "./files/brand-700.woff2", weight: "700", style: "normal" },
	],
	variable: "--font-brand",
	display: "swap",
});
```

```tsx
// src/app/[locale]/unitaid/page-content.tsx
import { brand } from "./fonts";

<h1 className={`${brand.className} text-5xl font-bold text-white`}>{t("title")}</h1>
```

Rules enforced by `npm run check:contract` (`[fonts]` group): font files only in `fonts/files/`, `.woff2` only, `next/font/local` only in `fonts/index.ts`, and never `next/font/google` (the build runs without network access). List every added family, its weights and licence in section 10 of the module's `INTEGRATION.md`. Details and conversion tips: `src/app/[locale]/unitaid/fonts/README.md`.

## Tests

The sandbox ships [Vitest](https://vitest.dev) so the module can carry its own test suite. Tests are optional: a repository with no test files passes `npm run test`.

```bash
npm run test         # run once (what CI does)
npm run test:watch   # watch mode while developing
```

Conventions, all enforced or assumed by `vitest.config.mts` and `npm run check:contract`:

- Test files are `*.test.ts` / `*.test.tsx` (or `*.spec.*`) placed next to the code they cover, or helpers and fixtures under a `__tests__/` folder, always inside `src/app/[locale]/unitaid/` or `src/app/api/unitaid/`. Files elsewhere fail the `[paths]` rule.
- Import `describe`, `it`, `expect` and `vi` from `vitest` explicitly; globals are off.
- Tests run in Node without a DOM, so they target `lib/`, `utils/`, `types/`, `services/` and the API routes. Component tests with `jsdom` and Testing Library need those packages approved first (see [New dependencies](#new-dependencies)).
- `@/...` resolves as in `tsconfig.json`, and `server-only` is mapped to an empty module, so code under `lib/` can be imported from a test.
- A test file is exempt from the `import "server-only"` rule under `lib/` and may touch `process.env` anywhere, but the `UNITAID_` prefix still applies. Prefer `vi.stubEnv` / `vi.unstubAllEnvs` over writing to `process.env`.
- Test files never reach the Global Malaria Dashboard: the import script leaves them out. Only the sandbox CI runs them.

The starter module contains three small examples: `lib/transform.test.ts`, `lib/env.test.ts` and `src/app/api/unitaid/_lib/store.test.ts`.

## Validation (local and CI)

```bash
npm run lint             # ESLint (next/core-web-vitals)
npm run format:check     # Biome (tabs, double quotes); `npm run format` fixes
npm run check:contract   # integration rules (folders, i18n, imports, env, dependencies)
npm run test             # Vitest (passes when the module has no tests)
npm run build            # production build, no network
```

The `.github/workflows/ci.yml` workflow runs the five commands on every push and pull request. A contract failure prints the group (`[paths]`, `[protected]`, `[i18n]`, `[imports]`, `[env]`, `[deps]`, `[fonts]`) and the file involved.

## Delivery

1. The five commands above are green.
2. The module's `INTEGRATION.md`, `README.md` and `.env.example` are filled in.
3. A release tag (`v1.0.0`, `v1.1.0`, ...) is created and recorded in the "Delivered version" row of `INTEGRATION.md`. The internal team imports that tag into the main project with the workflow described in [docs/main-repo/](docs/main-repo/README.md).

## For the maintainer (internal team)

| Command | When |
| --- | --- |
| `npm run module:init -- --slug <slug> --external-owner @org/team` | Once, right after creating a repository from the template. Renames the module, writes `module.config.json` and `CODEOWNERS`, regenerates the manifests. |
| `npm run host:sync -- --from <template checkout>` | To pull host changes from the template into a team repository (the `Sync host from template` workflow does this and opens a pull request). |
| `node scripts/check-contract.mjs --snapshot` | After changing any host file or approving a dependency in this repository. |
| `node scripts/check-contract.mjs --manifest-hash` | To get the value for the `PROTECTED_MANIFEST_SHA256` repository variable. |

Every snapshot changes the manifest hash: update the `PROTECTED_MANIFEST_SHA256` variable of the repository after merging. CI never runs `--snapshot`.

Repository settings (rulesets, CODEOWNERS, variables, Actions permissions): [docs/github/README.md](docs/github/README.md). Import into the main project: [docs/main-repo/README.md](docs/main-repo/README.md).
