# GitHub setup for a team repository

How the internal team creates and protects one sandbox repository per external team. The code enforces the contract in CI, but only the repository settings below make it binding: anyone with write access can edit the scripts, so the protections must live where the external team cannot change them.

## 1. Create the repository

1. Mark this repository as a **template** (Settings → General → Template repository).
2. **Use this template** → `rbm-module-<slug>` in the UNOPS organisation, private.
3. Clone it and run, as a maintainer:

   ```bash
   npm ci
   npm run module:init -- --slug <slug> --external-owner @UNOPS/rbm-module-<slug>
   npm run lint && npm run check:contract && npm run build
   git commit -am "chore: init module <slug>" && git push
   ```

   `module:init` renames every spelling of the placeholder module identity (`example-module`, `ExampleModule`, `EXAMPLE_MODULE_`), writes `module.config.json` and `.github/CODEOWNERS`, and regenerates the protected-files manifest. It prints the manifest hash used in step 3. The sample page, API routes and i18n texts are starter content for the team to replace.

## 2. Access

| Who | Role | Why |
| --- | --- | --- |
| `@UNOPS/rbm-dashboard-maintainers` (internal) | Admin | Edits settings, variables, rulesets; approves host changes |
| `@UNOPS/rbm-module-<slug>` (external) | Write | Creates branches and pull requests; approves module changes |
| External team lead (optional) | Maintain | Only if the lead should create release tags without the internal team |

Write access never allows merging into `main` directly once the ruleset below is active.

## 3. Repository variable

Settings → Secrets and variables → Actions → **Variables**:

| Name | Value |
| --- | --- |
| `PROTECTED_MANIFEST_SHA256` | the hash printed by `module:init` (or `npm run check:contract -- --manifest-hash`) |

Only admins can edit repository variables. CI passes it to `check:contract`, which fails when `scripts/protected-files.json` was regenerated by anyone else. Update it every time the internal team re-snapshots (host sync, approved dependency, template update).

## 4. Rulesets

Settings → Rules → Rulesets → **Import a ruleset**:

- [`ruleset-main.json`](ruleset-main.json): the default branch requires a pull request, one approval from the code owners, re-approval after the last push, the `Lint, contract and build` status check, and blocks force pushes and deletion. No bypass actors.
- [`ruleset-tags.json`](ruleset-tags.json): `v*` tags can be created, moved or deleted only by the Admin (`actor_id` 5) and Maintain (`actor_id` 4) roles.

With `CODEOWNERS` generated by `module:init`, a pull request that touches only the three module folders needs one approval from the external team. A pull request that touches anything else (scripts, `package.json`, `package-lock.json`, workflows, the shell) needs one approval from the internal team. The last matching pattern wins, so keep the file generated.

## 5. Actions

Settings → Actions → General:

- **Fork pull request workflows from outside collaborators**: require approval for all outside collaborators.
- **Workflow permissions**: read repository contents and packages permissions.

Never store a token with access to the Global Malaria Dashboard repository in a team repository. A workflow file pushed to any branch runs before the contract check can reject it. The import into the main repository therefore runs **from** the main repository, see [`../main-repo/`](../main-repo/).

## 6. Optional hardening

- **Organisation-level required workflow** that runs `npm run check:contract` from the template repository on every team repository. It cannot be edited or removed from a team repository and makes the manifest check independent of each repository's `ci.yml`.
- **Push rulesets** (organisation plan permitting) restricting `.github/**` and `scripts/**` to the internal team even on feature branches.

## 7. Keeping team repositories up to date

After changing host files in the template, run the **Sync host from template** workflow in each team repository (Actions → Sync host from template → Run workflow). It pulls the host files, re-applies the team's identity, re-snapshots and opens a pull request that the internal team reviews. After merging, update `PROTECTED_MANIFEST_SHA256` with the hash in the pull request body.

If the template repository is private, add a repository secret `HOST_SYNC_TOKEN` with read access to it (fine-grained PAT or GitHub App installation token).
